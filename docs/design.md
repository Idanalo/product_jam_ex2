# System Design: Parts 1 and 2

This document describes the database design, API specification, and game rules
for Part 1 (Tic-tac-toe) and Part 2 (Space pictures).

---

## Part 1: Tic-tac-toe Game Design (`big-three`)

### Variant Rules

- **Board:** 4×4 grid (16 cells, indexed `0..15`, with row $r \in [0, 3]$ and
  col $c \in [0, 3]$ where $\text{index} = r \times 4 + c$).
- **Players:** Two players on the same screen: **X** goes first, followed by
  **O**, alternating turns.
- **Winning Condition:** **Three in a row wins.** Any contiguous sequence of 3
  marks of the same player horizontally, vertically, or diagonally wins the game
  immediately:
  - **Horizontal wins (8 lines):**
    - Row 0: `[0, 1, 2]`, `[1, 2, 3]`
    - Row 1: `[4, 5, 6]`, `[5, 6, 7]`
    - Row 2: `[8, 9, 10]`, `[9, 10, 11]`
    - Row 3: `[12, 13, 14]`, `[13, 14, 15]`
  - **Vertical wins (8 lines):**
    - Col 0: `[0, 4, 8]`, `[4, 8, 12]`
    - Col 1: `[1, 5, 9]`, `[5, 9, 13]`
    - Col 2: `[2, 6, 10]`, `[6, 10, 14]`
    - Col 3: `[3, 7, 11]`, `[7, 11, 15]`
  - **Diagonal wins (main diagonals, top-left to bottom-right, 4 lines):**
    - `[0, 5, 10]`, `[5, 10, 15]` (from the main 4-cell diagonal)
    - `[1, 6, 11]` (offset diagonal above)
    - `[4, 9, 14]` (offset diagonal below)
  - **Anti-diagonal wins (top-right to bottom-left, 4 lines):**
    - `[3, 6, 9]`, `[6, 9, 12]` (from the anti 4-cell diagonal)
    - `[2, 5, 8]` (offset diagonal above)
    - `[7, 10, 13]` (offset diagonal below)
- **Draw Condition:** If all 16 cells are filled without either player achieving
  3 in a row, the game ends in a draw.
- **Move Validation:** A move is illegal if:
  1. The cell index is outside `0..15`.
  2. The target cell is already occupied.
  3. The game has already ended (a player won or all cells are filled).
- **Architecture:** All rules are implemented as pure functions in
  `shared/game/`. The React client uses them for gameplay, and the server uses
  the exact same functions to replay and verify moves submitted by the browser.

## Database

### Table `games`

Stores verified completed Tic-tac-toe games. Each row belongs to the user who
played/saved it.

| Column       | Type          | Rules                                                    |
| :----------- | :------------ | :------------------------------------------------------- |
| `id`         | `uuid`        | primary key, default `gen_random_uuid()`                 |
| `owner_id`   | `uuid`        | foreign key to `auth.users`, not null, on delete cascade |
| `moves`      | `jsonb`       | not null (ordered array of cell indices `0..15`)         |
| `result`     | `text`        | not null, check (`result in ('X', 'O', 'draw')`)         |
| `created_at` | `timestamptz` | not null, default `now()`                                |

- **Security & RLS:** Row Level Security is enabled with no public policies. The
  server uses the admin client and strictly scopes operations to
  `owner_id = c.get("user").id`.

---

### Table `apod_translations`

Stores Hebrew translations, summaries, and tags generated by Gemini for NASA
Astronomy Picture of the Day entries. Acts as a shared global cache so that
repeated requests for the same date never invoke Gemini again.

| Column                 | Type          | Rules                                                      |
| :--------------------- | :------------ | :--------------------------------------------------------- |
| `date`                 | `text`        | primary key (`YYYY-MM-DD`)                                 |
| `original_title`       | `text`        | not null                                                   |
| `original_explanation` | `text`        | not null                                                   |
| `hebrew_title`         | `text`        | not null                                                   |
| `hebrew_summary`       | `text`        | not null                                                   |
| `tags`                 | `jsonb`       | not null (array of 1 to 5 strings from allowed vocabulary) |
| `created_at`           | `timestamptz` | not null, default `now()`                                  |

- **Security & RLS:** Row Level Security is enabled with no public policies. The
  server controls all reads and writes.

## API Endpoints

### Part 1: Tic-tac-toe

#### `POST /api/games`

Submits a finished game's move sequence. The server replays the moves
step-by-step using `shared/game/`, verifies legality, determines the outcome,
and persists the record.

- **Method / Path:** `POST /api/games`
- **Requires Auth:** Yes
- **Receives (JSON body):**
  ```json
  {
    "moves": [0, 4, 1, 5, 2]
  }
  ```
- **Answers:** `201 Created` with:
  ```json
  {
    "id": "c138f36c-941d-4d22-83b3-f04bf4cfa123",
    "owner_id": "7694fbe2-...",
    "moves": [0, 4, 1, 5, 2],
    "result": "X",
    "created_at": "2026-11-04T18:00:00.000Z"
  }
  ```
- **Errors:**
  - `400 Bad Request`: If payload schema is invalid, or if the moves represent
    an illegal game (e.g. invalid index, move to an occupied cell, extra moves
    after game end, or game not finished). Error code: `"invalid_game"`.
  - `500 Internal Server Error`: If database insertion fails. Error code:
    `"database_error"`.
- **Tables:** Writes to `games` with `owner_id = c.get("user").id`.

---

#### `GET /api/games`

Returns the authenticated user's past games, sorted newest first.

- **Method / Path:** `GET /api/games`
- **Requires Auth:** Yes
- **Receives:** None
- **Answers:** `200 OK` with an array of game objects:
  ```json
  [
    {
      "id": "c138f36c-941d-4d22-83b3-f04bf4cfa123",
      "owner_id": "7694fbe2-...",
      "moves": [0, 4, 1, 5, 2],
      "result": "X",
      "created_at": "2026-11-04T18:00:00.000Z"
    }
  ]
  ```
- **Errors:**
  - `500 Internal Server Error`: If database query fails. Error code:
    `"database_error"`.
- **Tables:** Reads from `games` filtered by `owner_id = c.get("user").id`.

### Part 2: Space pictures

#### `GET /api/nasa/pictures`

Fetches random APOD pictures from NASA's API, and attaches any existing cached
Hebrew translations.

- **Method / Path:** `GET /api/nasa/pictures`
- **Requires Auth:** Yes
- **Receives (Query parameters):**
  - `count` (optional, integer 1-20, default `10`): Number of random APOD items.
- **Answers:** `200 OK` with an array of pictures:
  ```json
  [
    {
      "date": "2024-03-15",
      "title": "A Nebula in Orion",
      "explanation": "...",
      "url": "https://apod.nasa.gov/apod/image/...",
      "media_type": "image",
      "translation": {
        "hebrew_title": "ערפילית באוריון",
        "hebrew_summary": "...",
        "tags": ["nebula", "star"]
      }
    }
  ]
  ```
  _(If no translation is cached yet, `translation` is `null`.)_
- **Errors:**
  - `400 Bad Request`: If `count` is invalid.
  - `502 Bad Gateway`: If NASA APOD API fails. Error code: `"nasa_api_error"`.
- **Tables:** Reads from `apod_translations` to match any existing translations.

---

#### `POST /api/nasa/explain`

Retrieves or creates a Hebrew translation for a specific APOD date. The client
provides only the `date`. The server checks the DB cache first; if missing, it
fetches the original text from NASA, calls Gemini with structured output,
validates with Zod, saves to `apod_translations`, and returns the result.

- **Method / Path:** `POST /api/nasa/explain`
- **Requires Auth:** Yes
- **Receives (JSON body):**
  ```json
  {
    "date": "2024-03-15"
  }
  ```
- **Answers:** `200 OK` with:
  ```json
  {
    "date": "2024-03-15",
    "hebrew_title": "ערפילית באוריון",
    "hebrew_summary": "תמונה זו מציגה ענן גז ואבק ענק בחלל שבו נולדים כוכבים חדשים. האור הבוהק מגיע מכוכבים צעירים וחמים במיוחד.",
    "tags": ["nebula", "star"]
  }
  ```
- **Errors:**
  - `400 Bad Request`: If `date` is missing or invalid (`YYYY-MM-DD`). Error
    code: `"invalid_input"`.
  - `502 Bad Gateway`: If NASA APOD fails (`"nasa_api_error"`) or Gemini fails /
    returns invalid output (`"llm_error"`).
  - `500 Internal Server Error`: If database caching fails. Error code:
    `"database_error"`.
- **Tables:** Reads from and writes to `apod_translations`.

## Trade-off

**Global Translation Cache vs. Per-User Translation History:**

We considered whether `apod_translations` should be scoped per-user with an
`owner_id` or stored globally across all users keyed purely by `date`.

- **Per-User Caching:** Each user would have their own independent translations.
- **Global Caching (Chosen):** The primary key is solely `date`, without an
  `owner_id`.

**Why we chose Global Caching:**

1. **Cost and Rate Limits:** The assignment requires: _"Never pay twice for the
   same answer. Save the result in the database, and return the saved result the
   next time anyone asks for the same picture."_ If two different users request
   a translation for the same APOD picture, querying Gemini twice would waste
   LLM API quota and introduce latency for the second user.
2. **Deterministic Domain:** The NASA APOD title and explanation for a given
   calendar date are static and universal; the resulting 10-year-old Hebrew
   explanation and astronomical tags do not depend on user identity.
3. **Performance:** Serving cached translations from Supabase is instantaneous
   (~50ms) compared to an LLM roundtrip (~1.5-3s).

## What changed and why

1. **Gemini Model Endpoint**:
   - _Original Plan:_ Use `gemini-2.5-flash` for the LLM translation call.
   - _What Changed:_ When calling
     `https://generativelanguage.googleapis.com/v1beta/models/gemini-2.5-flash:generateContent`,
     Google's API returned a 404 error indicating that the legacy model is
     deprecated for new users. We queried the available models list via
     `/v1beta/models` and updated our endpoint to `gemini-3.5-flash-lite`, which
     fully supports structured outputs and provides faster latency.

2. **Server-Side Tag Sanitization Whitelist**:
   - _Original Plan:_ Rely solely on Zod schema checking for
     `tags: z.array(z.string())`.
   - _What Changed:_ Although structured output instructs Gemini to choose from
     the allowed tags list, LLMs can still hallucinate non-conforming strings or
     be swayed by prompt injection. We added an explicit server-side whitelist
     filter that verifies each tag against `ALLOWED_TAGS`, preventing unapproved
     or arbitrary tags from ever entering the database.

3. **In-Place Query Cache Updates for NASA Cards**:
   - _Original Plan:_ Invalidate `["nasa", "pictures"]` query after a
     translation was created.
   - _What Changed:_ Because `GET /api/nasa/pictures` returns a random set of
     pictures on each call, invalidating the query caused the entire page to
     re-roll and show different pictures, disorienting the user who just clicked
     "Explain". Instead, `useExplainNasa` performs an in-place
     `queryClient.setQueryData` update matching on `date`, instantly revealing
     the Hebrew translation on that card without changing the rest of the board.

4. **Tic-tac-toe Visual Polish**:
   - _Original Plan:_ Standard grid with background color highlighting on
     winning cells.
   - _What Changed:_ Added a ghost hover marker on empty cells to indicate whose
     turn it is, an animated SVG strike-through line connecting the winning
     3-in-a-row tiles, and mini 4×4 board thumbnails in the user's game history
     list to visually show the final board state of each saved game.

5. **GrannyGo Mobile Design and Responsive Desktop Layout (Part 3)**:
   - _Original Design:_ The Figma specification provided an isolated
     single-column mobile viewport (440px width) for the GrannyGo concept
     screen.
   - _What Changed:_ To support tablet and desktop screens seamlessly without
     distorting the mobile layout, the comparison sections (Waze pain points vs.
     GrannyGo benefits) and key features reflow into balanced 2-column grids on
     screens wider than 768px, while preserving the 46px rounded container,
     brand colors (`#3870b7`, `#ea383a`, `#0ea94b`), and Google Fonts
     (`Fredoka`, `Rubik`).
   - _Typography & Vector Assets:_ The designer's Figma file utilized a
     commercial Hebrew font (`Narkiss Block Condensed TRIAL`). To guarantee
     pixel-perfect visual fidelity across all browsers and devices without font
     rendering artifacts or requiring proprietary local font installations, we
     exported each typographic section directly from Figma as vector SVGs
     (`header-jam.svg`, `header-tagline.svg`, `ruti-title.svg`,
     `pain-points-block.svg`, `section-benefits.svg`, `voice-title.svg`,
     `pro-emergency.svg`, `pro-walk.svg`, `pro-grandchild.svg`,
     `pro-languages.svg`, and `footer-credits.svg`) and paired them with
     accessible semantic HTML, aria labels, and responsive CSS grid wrappers.

6. **Homepage Navigation & Overview (Part 4)**:
   - _Original Design:_ Starter kit placeholder content with placeholder text
     and sample event links.
   - _What Changed:_ Replaced with a unified overview dashboard showcasing
     Tic-tac-toe (Part 1), Space Pictures (Part 2), and Design to Code (Part 3),
     with direct navigation cards and global navbar integration.
